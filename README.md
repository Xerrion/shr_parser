# Signal Hound Spike Spectrum Analyzer SHR Parser

This Rust library parses and handles SHR files generated by Signal Hound Spike
software.
The SHR file format encompasses a file header and multiple sweeps, each with its own header and data.
The parser reads the file into an owned byte buffer and uses Rayon to process
sweeps in parallel. Changes to the source file cannot invalidate the buffer.

## Features

- **Parse SHR Files:** Read and interpret SHR files, including headers and sweeps.
- **Validate Files:** Ensure the integrity of SHR files by validating signatures and versions.
- **Sweep Metrics Calculation:** Compute key metrics such as peak, mean, and low values from sweep data.
- **Full Sweep Data:** Access every frequency/amplitude pair in each sweep, regardless of the selected summary metric.
- **Serialization & Deserialization:** Utilize Serde for seamless serialization and deserialization of SHR data.
- **CSV Export:** Export parsed SHR data to CSV format for easy analysis and reporting.

## Installation

To include this library in your project, add the following dependencies to your `Cargo.toml` file:

```toml
[dependencies]
shr_parser = "2.0.0"
```

## Usage

Here's an example of how to use the SHR file parser:

```rust
use std::path::PathBuf;
use shr_parser::{SHRParser, SHRParsingType};

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let file_path = PathBuf::from("path/to/your/shrfile.shr");
    let parser = SHRParser::new(file_path, SHRParsingType::Peak)?;

    println!("{}", parser.to_str());

    parser.to_csv(PathBuf::from("output.csv"))?;

    Ok(())
}
```

### Access all frequency/amplitude pairs

Each sweep retains all bins in `data`. Use `get_data()` to borrow the points without
copying them. Iterate over `parser.shr_file.sweeps` by reference to avoid the clones
performed by `parser.get_sweeps()`:

```rust,no_run
use std::path::PathBuf;
use shr_parser::{SHRParser, SHRParsingType};

fn main() -> Result<(), shr_parser::SHRFileError> {
    let parser = SHRParser::new(PathBuf::from("recording.shr"), SHRParsingType::Peak)?;

    for sweep in &parser.shr_file.sweeps {
        for point in sweep.get_data() {
            println!("{}, {}, {}", sweep.number, point.frequency_hz, point.amplitude);
        }
    }
    Ok(())
}
```

`frequency_hz` is calculated as `first_bin_freq_hz + bin_index * bin_size_hz`.
Amplitudes preserve the file's `f32` values in its reference scale (dBm or mV).
The existing `frequency` (MHz) and `amplitude` fields still contain the selected
Peak, Mean, or Low summary. `to_str()` and `to_csv()` still export summaries only.

NaN amplitudes remain in `data` but are excluded from all summary calculations.
For a nonempty sweep containing only NaN amplitudes, both summary fields are NaN.
Empty sweeps retain their zero-amplitude summary.

CSV filename metadata escapes carriage returns and newlines as `\r` and `\n`.
Names containing commas, quotes, carriage returns, or newlines are written as one quoted CSV field.

## Code organization

The implementation separates the serialized data model (`types`), header
formatting and validation (`header`), sweep summaries (`sweep`), binary file
decoding (`decode`), and the public parser and CSV interface (`parser`). The
existing public types remain available from the crate root.

Retaining all points increases memory use in proportion to the total number of
bins; the input byte buffer is also retained until parsing finishes.
Serialized sweeps now include `data`; older serialized sweeps without this
field deserialize with an empty `data` vector. Code that constructs `SHRSweep`
with a struct literal must supply `data` (or use `SHRSweep::new`).

## CI and releases

[CI](.github/workflows/ci.yml) runs on pushes to `main`, pull requests, and manual
runs. It checks formatting and Clippy, then runs tests and release builds on Linux,
macOS, and Windows. The workflows use nightly Rust to match `rust-toolchain.toml`.

[Release](.github/workflows/release.yml) runs when a `v*` tag is pushed. It verifies
that the tag matches the package version, runs CI, verifies the crate package,
publishes to crates.io, and creates a GitHub release with generated notes and the
`.crate` archive. Tags with a prerelease suffix create GitHub prereleases.

To release:

1. Configure a Trusted Publisher for `shr_parser` on crates.io with repository
   owner `Xerrion`, repository `shr_parser`, and workflow filename `release.yml`.
   Leave the environment unset; the publish job does not use a GitHub environment.
   The workflow uses GitHub Actions OIDC to obtain a temporary crates.io token;
   no `CARGO_REGISTRY_TOKEN` repository secret is needed.
2. Update the version in `Cargo.toml`, refresh `Cargo.lock` with `cargo check`, and
   update the installation example in this README. Use a version that has not
   already been published to crates.io.
3. Commit and push the changes, including the workflows. Wait for CI to pass.
4. Create and push a tag named `v` followed by the exact package version. For
   example, version `1.2.0` requires tag `v1.2.0`.

Publishing a crate version to crates.io is permanent. Do not push a release tag
until its commit is ready for publication.
